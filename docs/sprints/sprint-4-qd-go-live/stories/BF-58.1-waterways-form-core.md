## Technical Approach (scout, 2026-09-25T14:44:45Z)

Delta scout on top of the parent's scout of 2026-09-24. The parent's Build vs Use verdicts stand unchanged (copy the NDEP pattern; no new dependencies; `@react-pdf/renderer`, Zod 3 and `Intl` as installed). This section covers only what the split changed or what the parent did not reach. Recon at master `e2077eb`.

### Findings the parent did not have

1. **The backfilled projects will have zero sites.** After the migration, NDOT 4541 and RNO 18 show the Working in Waterways tab while `waterway_sites` is `[]`. The `new` page must handle that: no site selector, and a plain message that an admin adds sites in project setup (with a link for admins). Without it the first crew member to open the tab sees an empty required dropdown.
2. **Deploy order matters for the backfill.** `updateProject` deletes every `auto_permit` requirement row and re-derives from `PERMIT_FORM_MAP`. If the migration runs and someone edits NDOT 4541 or RNO 18 before the new code is live, the old map (`waterway: []`) deletes the backfilled row. Write the backfill as `INSERT ... ON CONFLICT (project_id, form_type) DO NOTHING` (the table has `UNIQUE(project_id, form_type)`), apply it right before the merge, and re-run it once after the production deploy. It is idempotent, so the second run is harmless.
3. **Photo `file_name` is an unconstrained string.** `photoSchema` accepts any `file_name`, and the inspector portal signs `projects/{id}/{sub}/{file_name}` with the **service-role** client. Supabase says it shipped storage path-traversal prevention on 2026-03-05 [verified 2026-09-25], but it does not say whether names containing `..` are rejected or taken literally. Do not depend on that. When the photo schema moves to a shared module (parent item 4), constrain `file_name` to the shape `PhotoAttachment` actually generates (`<digits>-<6 base36>.<ext>`, no `/`). Before tightening, check that every existing NDOT production record still parses (read-only query, with Tim's go), or the NDOT edit page starts rejecting old records.
4. **`photos.min(1)` proves a name was sent, not that a file exists.** Photos upload from the browser before submit, so the server only sees names. A cheap server check: `storage.from("form-attachments").list("projects/{id}/working-in-waterways", { search })` for each name, and reject any that are missing. Recommended, but the /story plan decides. The AC as written ("server rejects a submission with no photo") is met by `min(1)` alone.
5. **Copy NDEP's actions, not NDOT's.** NDOT's `updateNdotStormwater` does not chain `.select("id").maybeSingle()`, so an RLS-refused update reports success (Hot Gotcha). NDEP's does (BF-57). `collectFieldErrors` is already duplicated across the NDEP and NDOT actions; the third copy is the extraction trigger (service-layer rule).
6. **Pacific-date helper: use `formatToParts`, not the `en-CA` locale trick.** The ECMA-402 maintainers advise against relying on a locale happening to print `YYYY-MM-DD`, because CLDR data changes (tc39/ecma402#891). Build the string from `Intl.DateTimeFormat("en-US", { timeZone: "America/Los_Angeles", year: "numeric", month: "2-digit", day: "2-digit" }).formatToParts(now)`. Do not reach for `Temporal`: nothing in the repo uses it and its runtime availability was not checked. Put it in `src/lib/dates.ts` or similar; BF-58.2 and the follow-up ticket for the other five forms reuse it.
7. **Leave sites alone when the permit is unticked.** `buildProjectFields` rewrites the whole project on edit. If an admin unticks the Waterway permit, keep `waterway_sites` as is (do not clear it). Clearing loses setup data, and past submissions have their own snapshot anyway.
8. **The `waterway_sites` CHECK stays shallow.** `CHECK (jsonb_typeof(waterway_sites) = 'array')` in the database; element shape, non-empty names and de-duplication are validated by Zod in `parseProjectForm`. A per-element `jsonb_path_exists` CHECK is possible (PostgreSQL JSON path docs) but duplicates the Zod rules in a second language for a column only admins write.

### Interim guards (the split's new requirement)

As of `e2077eb`:
- `FormActions` renders the Download PDF button for every type. The PDF route answers a type with no template with HTTP 400.
- The inspector's `FormsTab` lists every submission, and the `FormDetail` fallback prints each key, with the photo array as raw JSON.
- `PHOTO_STORAGE_PATHS` in the inspector queries lists only `ndot_weekly_stormwater`.

Recommended guard, smallest change that BF-58.2 can remove cleanly:
- **PDF:** a `PDF_SUPPORTED` set next to `EDIT_SUPPORTED` in `form-actions.tsx`, same pattern. The button is hidden for `working_in_waterways` until BF-58.2 adds it to the set.
- **Inspector:** a `working_in_waterways` case in `FormDetail` that renders a short read-only summary (date, site name and descriptor, the four answers and comments, equipment text, and the number of photos), without photos. Do not exclude the type from the portal: the inspector's job is to see compliance records, and hiding a whole form type is the worse failure. BF-58.2 replaces the summary with the full renderer and photos.

`FormActions` also declares its own copy of the `FormType` union. Import it from `constants/permits` instead, so this story adds the type in one place, not two.

### Wiring checklist (from the parent's list, confirmed at `e2077eb`)

`FORM_TYPES`, `FORM_LABELS`, `PERMIT_FORM_MAP` (`waterway: ["working_in_waterways"]`) in `constants/permits.ts`; `FORM_ROUTE_MAP` in `ProjectTabs.tsx` and `dashboard/forms/page.tsx`; the `WATERWAY_PLACEHOLDER_KEY` sentinel and its tab removed from `ProjectTabs.tsx`; `FormType` and `EDIT_SUPPORTED` (plus the new `PDF_SUPPORTED`) in `form-actions.tsx`; `PHOTO_STORAGE_PATHS` stays for BF-58.2 unless the inspector summary needs it (it does not, photos are counted not shown); the PDF route's `FORM_TYPES.includes` check now admits the type and falls through to its 400 "template not available", which the hidden button makes unreachable from the UI.
